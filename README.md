# Peer-to-Peer Cue System #

Cue system for simple two-way communication and visual signaling using a WebRTC peer-to-peer connection.
This was initially designed for signaling on-stage actors during a theater performance.

Demo: https://jmcker.github.io/Peer-to-Peer-Cue-System

[PeerJS examples](https://peerjs.com/examples.html)

### Setup ###

1. Open receive.html on the receiving device.
2. Open send.html on the sending device.
3. Copy the ID from the receiving device to the sending device's ID field.
4. Press *Connect*.
4. Both should indicate a successful connection in the *Status* box.

### Features ###

The receiver has access to large indicators for standby, go, fade, and stop signals.

The sender has access to buttons that send the standby, go, fade, and stop signals, triggering the receiver's indicators.

Both have access to a two-way messenger for additional communication.

## Unified peer (fork experiment)

Open `peer.html` on both devices, scan the QR code with the second device, and press Connect. The first device must accept the incoming peer. Every device can initiate or accept multiple connections, select a recipient, send text and send visual cues. No account or transaction is required. The QR contains only a session URL, not an identity or secret. A connection ID is not authentication. Text and cues use the original string protocol; reserved cue words must be sent through the cue buttons. The original sender and receiver remain available, but their handling of untrusted HTML is not hardened; use the unified page for new-to-new connections. PeerJS signaling and NAT traversal remain external dependencies. QR generation is local using the vendored MIT qrcodejs copy (same revision used by Chisel).

Future Web3 feature: optional Chisel browser SDK for signed and encrypted typed messages, explicit action authorization and peer identity binding. It is not included in this pairing feature. Browser testing across Android and Chromebook is required before an upstream pull request.
